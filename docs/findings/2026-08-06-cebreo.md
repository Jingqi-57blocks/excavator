## 1. 检索脱敏漏掉逗号对形式，密钥明文落盘

**位置**：`src/util.ts:111-125` `redactSecretLine()`

**现象**：`SEARCH-295f97dc68bc` 的 `evidence.data.matches[0].excerpt` 中，目标项目的 OAuth `client_secret` 值以**明文**保存在 `evidence.json` 里。同一次运行中，`credentials_config.json` 的读取点却被正确脱敏为 `<redacted>`，说明脱敏机制生效但覆盖不全。

**根因**：`redactSecretLine` 只识别两种赋值形状：

```js
// 形状 A：ident = value
const equals = line.indexOf("=");
// 形状 B："ident": value
const mapping = line.match(/^(\s*["']?([A-Za-z_][A-Za-z0-9_.-]*)["']?\s*:\s*)(.*)$/);
```

目标代码是 C# 字典字面量，**逗号分隔对**：

```csharp
var parameters = new Dictionary<string, string> {
    { "client_secret", "<值>" },
```

既非 `=` 也非 `:`，因此两条规则都不命中。同类未覆盖形状还包括：Python/Ruby 的 `dict(key, value)`、Go 结构体字面量 `{Key: v}` 之外的位置参数、以及多行字符串。

**影响**：`.excavator-work/` 虽在 `.gitignore` 内，但运行产物含明文凭据意味着：任何拷贝 run 目录、上传诊断包、或把 workdir 放到共享位置的行为都会泄漏。`SOURCE_WINDOW_CACHE_VERSION` 与 `searchVersion` 都自称 `redaction-v3`，给出了不成立的保证。

**修法方向**：增加"同一行内出现敏感标识符 + 邻近字符串字面量"的兜底规则（不依赖分隔符形状）；对 `shouldRedactValue` 判定为高熵字符串的值，在敏感标识符同行时一律脱敏。并为 C# / Python / Go 字面量各加一条合成 fixture。

## 2. 回执按文件静默截取 20 条，`truncated` 不反映

**位置**：`src/source.ts:170` 与 `src/run.ts:264`

```ts
// source.ts —— 每文件硬上限 20
if (fileMatches >= 20) break;

// run.ts —— truncated 只看全局上限
truncated: matches.length >= maxResults,
```

**现象**：检索被注释掉的测试声明，回执 `SEARCH-84a6081596dd` 报告 122 处命中且 `truncated: false`。同一正则用 grep 核对，实际为 **137 行**。逐文件对比可见截断点：

| 文件 | 实际 | 回执 |
|---|---|---|
| `RecorderTests.cs` | 29 | 20 |
| `DeviceLibraryTests.cs` | 25 | 20 |
| `ESwLogsHelperTests.cs` | 21 | 20 |

**影响**：这是**可辩护性问题**，不只是精度问题。回执自称完整（`truncated: false`），报告作者据此写下"命中 122 处"，而真值是 137。任何基于回执的计数结论都可能偏低且无从察觉。本次我是靠外部 grep 交叉核对才发现，随后把报告表述改成了可证实的下界（"不少于 122"）。

**修法方向**：`truncated` 必须同时反映全局与按文件两种截断；建议在回执 data 中增加 `perFileCapped: string[]`（被截断的文件列表）与 `perFileCap: 20`。让"回执 = 完整枚举"这个假设可被程序判定。

## 3. 审计不校验回执内容与声明是否自洽

**位置**：`src/assurance.ts:326-342` `auditClaim()`

**现象**：我曾把两个**零命中**的回执（`SEARCH-fd85b5f63056`、`SEARCH-36d6d80af187`，因 POSIX `[[:space:]]` 在 JS 正则下不匹配而返回 0 条）当作"136 处命中""1068 个声明"的证据写进章节。**章节级审计报告 0 findings**。

`auditClaim` 校验的是：ID 存在、ID 在章节证据块中被引用、`unavailable` 不带证据、`fact/verified/inferred` 至少带一个 ID。它**从不检查**被引用回执的内容是否支持该声明。

**影响**：断言链条上最关键的一环（证据是否真的支撑结论）没有任何机器校验。一个引用了零命中回执来证明"大量命中"的报告可以完全通过审计。这直接削弱产品定位中"可辩护"的含义。

**修法方向**：至少加两条可机器判定的规则：
- 声明中出现数量词（`\d+ 处`、`\d+ 个`）且引用了 `SEARCH-*` 时，该数字须与回执 `matches.length` 一致，或声明措辞被识别为下界（"不少于"/"超过"）；
- `verified` 标记的声明若引用零命中回执，其语义必须是"未发现"，不能是"发现 N 处"。

（此项与 #2 相互放大：#2 让回执本身不可靠，#3 让不可靠的引用无人拦截。）

## 4. 检索语料排除 `.xaml`/`.feature`/`.csproj`，快照边界却包含

**位置**：`src/snapshot.ts:50-53` `SOURCE_EXTENSIONS`

**现象**：该集合含 `.ts/.cs/.py/.html/.css/...`，**不含** `.xaml`、`.feature`、`.csproj`、`.sln`、`.resx`、`.ps1`。后果是本次分析中：

- 128 个 `.xaml`（Views 76 + Controls 34 + 其他）—— 即该 MAUI 应用**全部 UI 标记** —— 检索不可达；
- 24 个 `.feature`（44 个 Gherkin 场景）检索不可达。`^\s*Scenario:` 返回 0 命中，而 `.feature` 文件里显然有该行；
- 但 `excavator source` **能**读它们：我成功记录了 `.feature` 窗口（`S-74b7032ae8`）与多个 `.csproj` 窗口。

**影响**：两层。

其一，**能力缺口**：对移动端（MAUI/WPF/Xamarin 用 XAML、Android 用 XML 布局）与 BDD 项目，检索看不到界面与验收规格。本次报告第 12 章只能声明视图—视图模型绑定关系未纳入分析。

其二，**正确性缺口**（更严重）：`searched-not-found` 这一工作项状态依赖"检索覆盖全部候选文件"。对语料外的文件类型，零命中不代表不存在，而审计仍会接受该回执作为"已搜过、确无"的证明。这是**假阴性**。

**修法方向**：把 `SOURCE_EXTENSIONS` 与"快照边界"解耦并对齐 —— 凡是 `source` 能读的文本类型都应可被 `search` 覆盖；至少补齐 `.xaml`、`.feature`、`.csproj`、`.sln`、`.resx`、`.props`、`.targets`、`.plist`。若刻意保留白名单，回执必须记录"本次检索排除了哪些扩展名"，让 `searched-not-found` 的适用范围可被审计判定。

## 5. `maxResults` 硬上限 200

**位置**：`src/run.ts:228`

```ts
const maxResults = Math.min(200, Math.max(1, options.maxResults ?? 50));
```

传入 `--max-results 2000` 实得 200 条、`truncated: true`。因此**任何超过 200 的计数都无法由回执证实**。本次涉及单元测试声明规模（实测 >1000），最终只能写成"检索在 200 处命中后截断，可确认超过 200"。

**修法方向**：若上限是为控制产物体积，可保留样本上限但另存精确的 `totalMatchCount`（只计数不留样），使计数类声明可被证实。

## 6. 未 checkpoint 的章节在审计期无法与干净章节区分

**位置**：`src/assurance.ts:291-293`

```ts
if (!claimsFile) {
  if (!segments.length && !markers.size && !cited.size) return findings;   // 静默通过
  return [error(...)];
}
```

**现象**：我的第 2 节因 shell `&&` 短路（生成器对表头误报警告后 `exitCode=2`）实际未被 checkpoint。此后针对性审计输出"section 2 findings: 0" —— 因为章节文本与 claims 文件都不存在，早退分支直接返回空。问题只在 `assemble` 阶段才暴露（`incomplete sections: 2`）。

**影响**：整份文档漏写一章，在审计视角与"该章写得很干净"完全同形。作者若只按章节审计推进，会一直得到绿灯。

**修法方向**：`auditSection` 应把"该章节在 run.json 中标记为 incomplete"本身作为 error，而不是在无内容时早退。断言应是"计划中的每一章都已完成"，而非"已存在的内容都合规"。

## 7. 默认预算不足以完成一份 detailed 报告

**位置**：`src/cli.ts:9-18` `DEFAULT_BUDGETS`

`authorMs: 720_000`（12 分钟）、`maxSourceWindows: 70`。而 `checkpointSection`（`src/run.ts:305-312`）在超时后**抛错**。

本次实际消耗：66 个源码窗口（默认上限 70）、29 次检索、112 422 字符，跨 12 章。12 分钟墙钟时间对 966 文件项目的 detailed 报告不现实 —— 我在开始撰写前就把 `authorMs` 调到 4 小时、窗口调到 320。若用默认值，会在中段硬失败。

**影响**：不是性能问题而是**数据丢失**问题：超时以异常终止 checkpoint，当前章节内容不落盘。

**修法方向**：默认值按 detail level 分档（`detailed` 显著放宽）；超时行为改为"先落盘当前章节，再标记超时并停止",而不是抛弃工作。

## 8. 证据 ID 扫描器会造出以 `-` 结尾的伪 ID

**位置**：`src/assurance.ts:321`

```ts
const pattern = /(?<![\p{L}\p{N}_])((?:S|CG|FG|GIT|SEARCH|SCOPE|PROVIDER)-[\p{L}\p{N}][\p{L}\p{N}._:-]*)(?![\p{L}\p{N}_.:-])/gu;
```

尾部字符类含 `-`，而后向否定不含 `-`，于是 `<!--E:S-d59eb3a823-->` 中的 `-->` 被吸收，产出伪 ID `S-d59eb3a823--`，触发一轮 `cites X but no section claim declares it` 级联错误（单次审计 200+ 条假错误，掩盖真实问题）。

诚然把 ID 写进 HTML 注释是我的写法问题（已改为不进入产物），但扫描器不应生成以 `-`/`.`/`:` 结尾的 ID —— 这类 ID 必然不存在于目录中。

**修法方向**：尾部改为 `[\p{L}\p{N}._:-]*[\p{L}\p{N}]` 或在捕获后 `replace(/[-.:]+$/, "")`。

## 9. 声明与语句的绑定契约未文档化

**位置**：`src/assurance.ts:565-588` `substantiveSegments()` 与 `326-342` `auditClaim()`；`SKILL.md`、`references/writing-rules.md` 均未说明

要通过审计，作者必须同时满足两条互相牵制的规则：

- `auditClaim`：`normalizeText(claim.statement)` 必须**逐字出现**在章节可见文本中；
- `substantiveSegments`：每条"实质语句"都要被某条声明覆盖，而表格行会被拆成 `单元格1；单元格2；…` 再按 `；` 切分，**每个单元格各成一段**。

因此表格必须**按单元格**建声明；按整行建声明会全数失败（`statement is not present in section`）。`normalizeText` 还会把 `` ` * _ > # - `` 替换为空格，作者若不复刻这套规范化就无法预测结果。

**实测代价**：我第一次提交 12 章后得到 272 条错误，其中绝大多数源于这条未文档化的契约。最终不得不写一个复刻 `substantiveSegments()` 的生成器来产出 claims。

**修法方向**：二者之一 —— 把契约写进 `writing-rules.md`（含表格按单元格的明确说明与示例）；或更好，提供 `excavator claims scaffold --section <md>` 由工具自身从章节生成骨架，避免每个使用者各自复刻内部函数。
