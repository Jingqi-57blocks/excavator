## 一、可辩护性链条上的实质缺陷

### 1. `assemble` 是全有全无的，导致审计在完工前无法使用

**位置** `src/run.ts:391-394`

```ts
for (const document of manifest.documents) {
  const reportPath = join(runDir, "reports", reportFileName(document));
  if (!await exists(reportPath)) {
    findings.push({ level: "error", document: document.id, message: "assembled report is missing" });
    continue;
  }
  ...
```

**问题** 这个 `continue` 跳过了该文档后续的**全部**检查，其中包括填充 `claimsByDocument`。于是只要有任意一份文档尚未组装，`auditWorkItemClaimCoverage` 就会把**所有**工作项判成"未被任何断言覆盖"。

**实际观察** 本次跑出 29 条这样的假 error，全部在最后一份文档组装完成后自动消失。

**后果** 25 份文档的运行中，前 24 份拿不到任何可信的审计反馈，问题只能在最后一刻一次性暴露。本次实际的规避办法是在 scratchpad 里写预检脚本直接调用 `assurance.ts` 的导出函数，绕开 `assemble` 完成度校验。

**建议方向** 让审计支持"部分组装"模式：缺失文档只降级为 warning，且不影响其余文档的断言覆盖统计；或提供 `excavator audit --document <id>` 的单文档审计入口。

---

### 2. 两处证据层级检查规则不一致，且文档级检查形同虚设

**位置**

- 段落级 `src/assurance.ts:597` `markersIn`
  ```ts
  if (/(?:`事实`|\bfact\b)/i.test(text)) markers.add("fact");
  if (/(?:`验证`|\bverified\b)/i.test(text)) markers.add("verified");
  if (/(?:`推断`|\binferred\b)/i.test(text)) markers.add("inferred");
  if (/(?:`不可得`|\bunavailable\b)/i.test(text)) markers.add("unavailable");
  ```
  **要求反引号**。

- 文档级 `src/run.ts:401`
  ```ts
  if (!/事实|推断|验证|不可得|fact|inferred|verified|unavailable/i.test(text))
    findings.push({ level: "warning", document: document.id, message: "no visible evidence-level wording was found" });
  ```
  **不要求反引号**。

**问题** 文档级正则会被正文中任意一个"验证""校验"之类的普通中文词偶然满足，约束不到任何真实质量。

**实际观察** 本次触发 18 条该 warning。规避办法是在受影响章节末尾追加一句**不带反引号的、包含这四个词的普通句子**，检查随即通过。这证明该检查不具备实质约束力。

**后果** "证据层级已标注"这一审计结论目前不可信。修复后存量文档大概率会掉出绿灯。

---

### 3. 发布的 claim schema 与运行时产物互不兼容

**位置** `schemas/claim.schema.json` 与 `src/types.ts` `SectionClaim`

**schema 侧**

```
properties : id, schemaVersion, statement, marker, findingIds, evidenceIds, documentId, section, reason, supersedes
required   : id, schemaVersion, statement
additionalProperties: false
```

**运行时侧**

```ts
export interface SectionClaim {
  id: string;
  marker: EvidenceMarker;
  statement: string;
  evidenceIds?: string[];
  traceIds?: string[];      // schema 中不存在
  workItemIds?: string[];   // schema 中不存在，但审计强制要求
  confidence?: Confidence;  // schema 中不存在
  status?: "candidate" | "verified" | "unavailable";  // schema 中不存在
  reason?: string;
  supersedes?: string;
}
```

**实测** 用 ajv(2020) 校验本次真实产出的断言文件：

```
emitted claim keys: evidenceIds, id, marker, statement, workItemIds
keys rejected by additionalProperties:false -> workItemIds
required keys absent -> schemaVersion
emitted claim (with traceIds+workItemIds) valid? false
errors:  must have required property 'schemaVersion'
```

**结论** 这个工具产出的**每一条断言**都通不过它自己发布的 v1 schema。其中 `workItemIds` 正是 `auditWorkItemClaimCoverage` 强制要求的字段——schema 禁止的东西，审计却要求。

**根因** `tests/schemas.test.ts` 只用 `schemas/examples/` 下的手写 fixture 做正反例校验，从未拿真实 run 产物校验过。测试通过与契约正确之间没有关联。

**建议方向** 在测试中增加一条：跑一次最小 run，用发布的 schema 校验其全部产物。

## 二、取证质量

### 4. 密码脱敏误伤合法证据，且不可关闭

**位置** `src/util.ts:106-125` `redactSecrets` / `redactSecretLine`，作用于搜索摘录（`src/source.ts:167`）和源码窗口，无开关。

**判定逻辑** 只看标识符名经 `isSensitiveIdentifier` 归一化后是否命中敏感词表，不看值是否真的敏感。

**实测**

```
"pto_token: DataTypes.FLOAT,"                              -> "pto_token: <redacted>,"
"  TbToken = \"tb_token\""                                  -> "  TbToken = <redacted>"
"const oauth2TokenEndpointGrantRefresh = \"refresh_token\";" -> "const oauth2TokenEndpointGrantRefresh = <redacted>;"
"mcpToken: {"                                              -> "mcpToken: <redacted>"
"refresh_token_expires_in: 3600,"                          -> "refresh_token_expires_in: 3600,"   (未误伤)
"API_KEY=abcd1234"                                         -> "API_KEY=<redacted>"                (正确)
```

**危害排序**

1. `mcpToken: {` —— **开括号被吞掉**，整个模型定义在证据里变成断头结构，后续字段行悬空。
2. `pto_token: DataTypes.FLOAT` —— `pto_token` 是"调休小时数"业务字段，`DataTypes.FLOAT` 是关键事实，直接丢失。
3. `TbToken = "tb_token"` —— 表名常量，是追踪存储路径的必要线索。
4. `oauth2TokenEndpointGrantRefresh = "refresh_token"` —— OAuth 授权类型常量，是分析令牌端点分支的核心证据。

**建议方向** 值侧判定优先于名侧：只有当值形如高熵字面量时才脱敏；对 `{`、`[`、类型表达式、已知枚举字符串一律放行。同时提供显式开关。

---

### 5. 表格单元的断言绑定方式反直觉

**位置** `src/assurance.ts:565` `substantiveSegments`

```ts
line = line.slice(1, -1).split("|").map((cell) => cell.trim()).filter(Boolean).join("；");
```

表格行先被按 `|` 拆成单元格、用 `；` 拼回，再按 `/(?<=[。！？!?；;])\s*|(?<=\.)\s+(?=[A-Z0-9])/u` 切分。

**后果**

- "一行一条断言"这种最自然的写法**永远匹配不上**——断言里用 ` | ` 连接的文本无法对上以 `；` 结尾的分片。必须**每个单元格一条断言**，断言因此变得语义稀薄。
- **表头单元格也会被当成需实质断言的内容**。本次"运行单元与技术栈"刚好 8 个语义字符，达标入选，规避办法只能是**把表头文字改短**。这是让内容迁就校验器。

**建议方向** 表格行整体作为一个可绑定单元，或对表头行（`|---|` 的上一行）显式豁免。

---

### 6. 8 字符阈值对中英文不等价

**位置** `src/assurance.ts:584`

```ts
if (semanticLength >= 8) segments.push(normalized);
```

`semanticLength` 数的是 `\p{Letter}\p{Number}` 字符数。

**问题** 中文 8 字 = 一个完整短语；英文 8 字符 = 一个单词。同一阈值在两种语言下的语义粒度差一个数量级。

**实例** `wcp-auth` 只有 7 个语义字符，豁免；中文表头 8 个字，反而被要求断言。

**建议方向** 按脚本类型分别设阈值，或改用分词后的词数。

---

### 7. `normalizeText` 破坏标识符

**位置** `src/assurance.ts:606`

```ts
function normalizeText(value: string): string {
  return value.replace(/[`*_>#-]/g, " ").replace(/\s+/g, " ").trim();
}
```

把 `` ` ``、`*`、`_`、`>`、`#`、`-` 全替换成空格。

**后果** `wcp-service-v2` → `wcp service v2`，`<token>` 的下划线类修饰丢失。断言文本与章节文本的匹配在标识符上是模糊的——既可能漏配，也可能误配到不同的标识符上。

**建议方向** 仅剥离行首 Markdown 结构标记，不对行内字符做全局替换。

## 三、预算与规模

### 8. 默认预算对任何真实项目都不可用，且不随文档数缩放

**位置** `src/cli.ts` `DEFAULT_BUDGETS`

```ts
const DEFAULT_BUDGETS: BudgetConfig = {
  prepareMs: 180_000,
  authorMs: 720_000,
  maxGraphQueries: 40,
  maxSourceWindows: 70,
  maxSourceCharacters: 160_000,
  maxFiles: 100_000,
  maxFeatureNodes: 220,
  maxExpansionDepth: 2
};
```

**实际观察** 23 个功能的 `prepare` 在默认值下直接失败：

```
{"error": "CodeGraph query budget exceeded (40)"}
```

40 次图查询连"每个功能查两次"都不够。

**本次实际写入请求的值**（`run.json` 实测）

| 预算项 | 默认 | 实际需要 | 倍数 |
|---|---|---|---|
| `maxGraphQueries` | 40 | 2000 | 50× |
| `maxSourceWindows` | 70 | 4000 | 57× |
| `maxSourceCharacters` | 160 K | 20 M | 125× |
| `authorMs` | 12 min | 6 h | 30× |
| `prepareMs` | 3 min | 90 min | 30× |

功能轮 timeline 实际跨度 **2.9 小时 / 561 个事件**。

**核心问题** `authorMs: 720_000`（12 分钟）是**整个 run** 的预算，不是每份文档的——25 份文档共享 12 分钟。这套默认值显然是照"单文档 demo"定的，缺少按 `documents.length` 缩放的逻辑。

**建议方向** 预算按文档数派生（如 `authorMs = perDocumentMs × documents.length`）；`prepare` 失败时在错误信息里直接给出建议值。

---

### 9. `maxFeatureNodes: 220` 静默截断

每个功能的候选节点数都精确停在 220。没有任何"被截断了多少""截掉的是什么类型的节点"的信号。

**后果** 无法判断某个功能的边界是自然收敛出来的，还是撞上限撞出来的——这两者对报告可信度的含义完全不同。

**建议方向** 截断时记录一条 timeline 事件并在 context 文件头部标注"已截断，原始候选 N 个"。

---

### 10. 功能边界构建被通用动词淹没

**位置** `src/context.ts:530` `GENERIC_FEATURE_ACTION_TERMS`（仅 20 个词）、`src/context.ts:619` `tokenize`

```ts
const GENERIC_FEATURE_ACTION_TERMS = new Set([
  "approval", "approve", "approved", "reject", "rejected", "withdraw", "withdrawal", "cancel", "cancellation",
  "create", "update", "delete", "list", "detail", "manage", "management", "process", "workflow",
  "审批", "批准", "拒绝", "撤销", "取消", "创建", "更新", "删除", "管理", "流程"
]);
```

**实际观察** 几乎每个功能的候选集都被 auth / route 样板文件占满。最典型的是 legacy worklog：它的**全部实现都不在 prepare 出来的边界内**，只能事后靠 `excavator search` 手工捞回。

**附带问题** `tokenize` 的 `/[\p{Letter}\p{Number}_-]{2,}/gu` 不含 `.`，别名里带文件名会被拆词。

**建议方向** 停用词表改为从目标语料统计 IDF 动态生成，而非硬编码。

## 四、工作流与运维

### 11. 工作目录改版无迁移、无警告，直接吃掉历史 run

切换到 `.work/<target>/runs/` 布局后，原 `.work/runs/` 下的整棵树消失，其中包含**一次已审计通过（0 error / 0 warning）的完整 overview 运行**。两份 overview 只能重跑。

**后果** 对一个以"append-only 哈希链、可辩护"为卖点的工具，静默丢弃历史运行是自相矛盾的。

**建议方向** 布局变更提供迁移命令；发现旧布局残留时至少打印警告而非无视。

---

### 12. 无法向已有 run 追加文档

中途需要补文档只能新开一个 run。

**实际后果** 本次一个交付物横跨**两条独立的保证链**（功能 run + overview run），两次审计、两套 timeline，最后靠人工把它们拼进同一个站点。从可辩护性角度，这个站点没有单一的完整性根。

**建议方向** 提供 `excavator extend --run <dir> --feature ...`，在同一分析范围与哈希链下追加文档。

---

### 13. 必需工作项的 trace 要求缺少前置可见性

**位置** `src/assurance.ts:509` `auditWorkItems`

```ts
["normal-flow", "decision-flow", "reversal-flow", "states-and-lifecycle", "notifications-and-exports"]
```

这五类工作项在 `found` 时必须有 verified trace。

**问题** 该要求**只在审计时暴露**，prompt 与 `workitems.json` 中都看不出来。

**实际观察** 写完第一份文档跑审计才发现少了 `states-and-lifecycle` 和 `notifications-and-exports` 两条 trace，此后每份文档都需预留 5 条。

**建议方向** 在生成的 prompt 与 workitems.json 里显式标注 `traceRequired: true`。

---

### 14. 子命令不支持 `--help`

```
$ excavator feature --help
{"error": "Missing --subject"}
```

只有顶层 `excavator help` 可用，每个动词的参数只能读源码确定。

## 五、HTML 输出

### 15. 多 run 合并时导航序号冲突

**位置** `packages/excavator-html/src/renderer.ts:38`

```ts
pages.sort((a, b) => a.order - b.order || a.title.localeCompare(b.title));
```

`order` 取自各自 run 的 front matter。本次 overview 是 1-2、功能是 1-23，合并时直接撞车，且没有按文档类型（overview 优先于 feature）的兜底优先级。

**实际后果** 手工重编号 25 个文件的 front matter。

---

### 16. 中文外壳残留英文 aria-label 与外网 CDN 依赖

**位置** `packages/excavator-html/src/renderer.ts:70-72`

**已本地化** 可见文案全中文：本页目录 / 功能模块 / 图表详情 / 关闭。

**未本地化** 三个 aria-label 仍是英文：`Report modules`、`Table of contents`、`Back to top`。屏幕阅读器用户拿到的是混合语言界面。

**外网依赖** mermaid 从 `https://cdn.jsdelivr.net/npm/mermaid@11/...` 加载。离线环境下所有图表退化为"图表无法渲染。请连接网络后重新加载。"——**这个降级文案本身是中文的**，说明离线场景已被预期到，却没有内联方案。

## 优先级判断

优先修复 **1、3、4**：

- **1** 让审计在完工前不可用，直接影响长运行的可操作性；
- **3** 让发布的契约与实际产物互相打脸，是对外承诺层面的问题；
- **4** 让证据本身失真，动摇"可辩护"这个核心命题。

**2** 更麻烦一点：它意味着现有的"证据层级已标注"审计结论**目前不具备约束力**。修复之后，存量文档大概率会掉出绿灯——这是必要的代价，但需要预期到。
