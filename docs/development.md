# Excavator 开发流程

> 本文件是开发循环的权威表述。与 Linear 项目描述冲突时，方向问题以 Linear 为准，流程问题以本文件为准。

## 模型分工

**Fable 5 = 脑力活（一切判断性决策），Opus 5 = 体力活（一切产出性工作）。**

1. **判断性决策** → Fable：制定方案、失败归因分诊、评审裁决、验收边缘解释、规划层分析、闸门建议。
2. **机械条件** → 现场读取，不惊动 Fable：测试绿不绿、checkbox 全不全。
3. **产出性工作** → Opus：编码、测试、证据收集、汇编、合并操作、Linear checkbox。

边界：方案框定范围内的微观选择（命名、局部结构）Opus 自主；超出方案框架的选择即升级 Fable——"是否在框内"拿不准时也算超框。

代理定义见 `.claude/agents/`：planner（fable）、reviewer（fable）、coder（opus）。

## 状态转移表

| 节点 | 执行者 | 做什么 | 出口 → 去向 |
|---|---|---|---|
| **S 取任务** | Opus | 从看板取未阻塞任务 | 有 → 1；无但有挂起 → 触点二；全空 → 停 |
| **1 制定方案** | **Fable** | 范围 / 非范围 / 测试计划，对照护栏，写入 PR 描述 | 一致 → 2；可修 → 1；规划有问题 → G |
| **2 开发** | Opus | 实现 + 测试同批，`57B-xxx:` 格式 | 完成 → 3 |
| **3 自测** | Opus | 全量测试、真实冒烟、合同正反样例，证据入 PR | 全绿 → 4；失败 → T |
| **T 失败归因** | **Fable** | 判定失败性质 | 代码问题 → 2；预期/规划问题 → G |
| **4 评审** | **Fable** | 审 Opus 的 diff：缺陷 + 护栏逐条（敏感面加 security-review） | 通过 → 5；缺陷/越界 → 2；护栏存疑 → G |
| **5 合入 feat** | Opus | 合并，Linear 自动流转 | issue 未完 → S；完 → 6 |
| **6 验收** | Opus 跑 / **Fable** 判 | 逐条执行验收标准出证据；边缘案例 Fable 解释 | 满足 → 勾 checkbox：Phase 未完 → S，完 → 7；实现缺口 → 1；标准存疑 → G |
| **7 收口** | Opus | 全量回归 + 汇编 feat→main PR | 绿 → 触点一；否 → 修后重跑 7 |
| **G 规划层分析** | **Fable** | 能改方案就改；需用户则起草裁决材料 | 修订 → 1；需裁决 → P |
| **P 挂起** | — | 起草裁决材料呈给用户 | → S |
| **触点一** | 用户 | 审 feat→main PR（证据汇总），合并 | → 闸门判定或下一 Phase |
| **触点二** | 用户 | 收打包裁决请求（仅当全部任务被阻塞） | 裁决后 → S |
| **闸门** | Opus 收数据 / **Fable** 出建议 / 用户决定 | 执行闸门 issue 的清单 | 放行 → 新 feat → S；不放行 → 触点二 |

## 横切硬规则

- 不许删除或跳过既有测试来保绿；测试失败如实报告。
- 范围外发现在 PR 里报告，不顺手做。
- Linear 只记结果：状态自动流转、交付物 checkbox、闸门决策记录；过程性内容（计划、证据、冒烟输出）全在 Git / PR。
- main 的入口只有用户。

## 文档

**不为过程创建文档。** `docs/` 只放确定不变的东西；一切会随代码变的说明写在代码里。

- 不写：待裁决清单、决策归档、调研记录、问题清单、状态报告、验收记录、阶段计划、测试域清单。这些的位置是 Linear、PR 描述、或者一次性的对话回复。
- 不写：任何转述代码的机制说明——运行流程、产物形状、命令清单。代码是唯一真相，转述只会漂。
- 删掉一份文档时，同一次改动里清掉它的全部引用（`grep -rn` 文件名，含裸名与带 `docs/` 前缀两种），不留指向不存在文件的规则。
- 判据：这份文档下个月还对吗？会随代码变的答「不」，那就不建。

## Git 与 PR 约定

1. main 只能通过 feat 分支合并进入，禁止直接 push main。
2. 一个大 feature 用一条长期 feat 分支；过程中的 PR 先合并到 feat 分支，最后 feat → main。
3. commit message 与 PR title 固定格式：`<Linear ID>: <描述>`。commit 含 Linear ID 即自动关联，状态自动流转，不手动更新 Linear。
4. PR 粒度按工作量裁定：重 issue 可拆多个 PR（关联同一 ID）；编码类 issue 至少一个 PR；纯决策类可以没有 PR。
5. 实现与测试同一批提交；新逻辑开新文件、单一职责；注释只加关键处。

## 自动化时机

流程先手动会话驱动，验证跑顺后可用 `/ralph-loop` 包装无人值守（completion promise = 到达触点一或触点二时输出）。目标外置于看板，无需额外 goal 设置。
