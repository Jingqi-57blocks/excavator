1. 项目定位与边界

  • WCP 当前快照由一个统一前端、一个主平台服务、一个早期 Node 服务、一个绩效与晋升服务和一个身份服务共同组成。事实
  • 当前源码覆盖员工自助、项目与客户、工时、请假、行政申请、报销、账单、招聘、绩效与晋升等组织活动。事实
  • 生产环境实际启用的入口以及组织如何定义新旧服务并存阶段不在静态快照中。不可得

2. 系统组成与职责

  • 前端把员工自助、项目跟踪、公司内容和管理后台组合为同一用户界面。事实
  • 主平台 Go 服务承载范围最广的业务 API，早期 Node 服务仍注册工时、项目、请假、假期、报表和集成入口。事实
  • 绩效服务与身份服务保持独立路由边界。事实

3. 业务域与功能地图

  • 前端菜单把能力分为个人工作、项目跟踪、公司内容和管理操作。事实
  • 个人工作包含工时、请假、行政申请和报销，管理能力包含项目、招聘、账单、审批、工时表和员工管理。事实
  • 静态路由与节点清单还覆盖绩效、晋升、身份、文件、通知和后台任务。事实

4. 用户、角色与权限边界

  • 主平台定义普通员工、管理员、项目管理、人力资源、绩效管理员、客户、销售、费率管理、办公室管理、发票管理和系统管理员等角色。事实
  • 前端对项目、招聘、账单、审批和员工管理菜单声明了不同的角色集合。事实
  • 请假等业务还在服务函数内执行对象级审批人、本人、管理员和人力资源判断。事实
  • 完整的角色乘以入口乘以业务对象权限矩阵尚未由本次静态审查建立。不可得

5. 核心业务对象与生命周期

  • 当前产品围绕员工、项目、项目成员、工时、请假、假期额度、审批、账单、绩效记录和候选人等对象工作。事实
  • 请假对象连接申请人、项目、假期类型、日期、小时、审批记录、额度记录和附件引用。事实
  • 请假生命周期包含多级待审、批准、拒绝、完成、取消和等待负责人同意取消等状态。事实

6. 数据全景与流转

  • 主平台 Go 模型和早期 Node 模型都映射到请假、请假明细和年度假期额度等同名数据表。事实
  • 这表明同一业务数据形状由多个服务实现直接映射；是否都在生产写入同一个数据库实例无法由静态源码确认。事实
  • 文件、导出、邮件和移动通知会把部分业务内容交给对象存储或外部消息能力。事实
  • 生产数据库拓扑、数据保留期和租户隔离方式不在源码快照中。不可得

7. 外部依赖与集成

  • 主平台初始化包含数据库、对象存储、邮件、Google 服务和后台任务等外部依赖。事实
  • 早期服务依赖邮件、Slack、Jira 和定时任务，并通过环境配置控制部分行为。事实
  • 应用代码中的失败处理并不统一，有些路径返回错误，有些异步执行只启动 goroutine。事实

  • 系统提供审批、员工与项目维护、招聘、账单、导出、政策内容和周期性任务等后台能力。事实

9. 风险与当前状态

  • 主平台源码包含一个固定的对称加密密钥字面量，并由加密和解密函数共同使用。事实
  • 部分运营和分析行为直接依赖办公室、项目或客户的固定数字标识。事实
